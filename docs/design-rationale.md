# Design rationale

Why each constant has its value and each invariant exists. One entry per item: the number, the
reason, the file it governs. Engine limits live in `CONTEXT.md`; benchmark runtime facts in
`ops/hydradb/step-load-2026-08.md`; this file is what was in the code comments before the 2026-09-04
cleanup (`d8a6e42`, `b3aa850`) and is not anywhere else. Dates mark decisions taken from a measurement.

## packages/hydra

**Retry schedule** (`Transport.ts`). Engine failures that declare themselves retryable
(`write_conflict`, `writer_unavailable`, `writer_lease_unavailable`, `object_store_unavailable`) are
capacity answers, not wrong statements. Jittered exponential backoff from 100 ms, 7 attempts, ~6 s
total, inside the 30 s runtime cap. Replay is safe because every write is a content-addressed
`MERGE` with a fresh `query_id`. Before this existed a three-user ingest lost four whole users in
its first minute.

**Body budget** (`Chunking.ts`). Rows are chunked so each statement stays inside *both* the 1 MB
HTTP body cap (80 % of it) and the 30 s runtime cap; the two batch forms have different per-row
costs, so each declares its own row ceiling.

**`MERGE_ROWS_PER_CHUNK = 1000`** (`Chunking.ts`). Set by admission control (1024), not throughput:
on a fast node 500 vertex upserts take ~55 ms and 1 000 edge upserts ~40 ms even at a million edges.
On the durable benchmark runtime a full chunk crossed the 30 s cap around the ninth user, so the
batch halves on a limit refusal and *keeps* the smaller size for the rest of the write — one slow
failure per write, not one per chunk.

**`DELETE_ROWS_PER_CHUNK = 40`** (`Chunking.ts`). `DETACH DELETE` costs whatever the vertex's degree
is (a high-`df` Token sits on thousands of edges), so no fixed size is safe: 100 keys is instant for
Claims and past the 30 s cap for Tokens. The batch halves on a limit error and keeps the size; the
store-wide `delete_vertex_scan_edges` limit is not halvable, so that one fails loudly.

**`MAX_RESULT_PAGES = 200`** (`Paging.ts`). 200 × 1024 = 204 800 rows, past the engine's own 100 k
result-vertex cap. Hitting it is an **error**, not a stop: returning what was gathered would be the
1024-row wall one order of magnitude up. `followCursor` needs the cursor *and* the `query_id`; an
empty page with no cursor is the end.

**Oversize-property check is client-side** (`Cypher.ts`, `MAX_STRING_PROPERTY_BYTES = 32_743`). The
engine answers 32 744 bytes with a bare 500 `internal query execution error`; the cap is bytes, not
code points (16 371 two-byte characters is the same boundary). Found by bisection.

**Bookmark is a `FiberRef`, not a `Ref`** (`Client.ts`). A causal token belongs to the request that
received it. A process-wide ref would make one user's write a floor for every unrelated read and
would not survive server replicas.

**Errors are classified by message, not status** (`Transport.ts`). The engine changed a timeout from
500 to 408 once already; the message test survives that. "Statement too big" (a `HydraLimitError`,
retryable by splitting) must stay distinct from "engine down" (not), because `writeChunked` and
`deleteByKeys` halve only on the former. A 5xx body is not a contract: `reason` is generated by the
client, never copied from the wire into a log or receipt. Parse errors are the exception — the
engine names the exact rule broken, so they are carried verbatim.

**Identity guard is process-local** (`Client.ts`, `Ids.ts`). Ids are the top 53 bits of
`SHA-256(key)` (JSON numbers cannot carry a u64). A pre-write remote probe is not expressible
(`CONTEXT.md`, unlabelled `MATCH`) and would be ~8 × 10⁵ vertex plus ~2.5 × 10⁶ edge round trips at
~100 ms each — months, for a graph the batched writes place in an hour. The guard that survives is a
map from numeric id to key that fails a *different* key hashing to a claimed id; the persisted
`__palimpsest_full_key` is verified on every read (`getById`, `verifyPathIdentity`). Uncaught: a
collision that exists only across two separate processes' write paths — ~5 × 10⁻⁵ at 10⁶ vertices.

**Re-chunk only what is left** (`test/unit/write-chunking.test.ts`). Every other test refuses the
*first* chunk, so `chunks.slice(index)` was never exercised; `chunks.flat()` passed them all while
production re-sent every committed row and reported `written` larger than the payload.

## packages/llm

**Three read-path model ids, one default** (`Models.ts`). Reader, selector and sufficiency check are
different jobs and each is separately overridable, but they default to one model so that setting
nothing is the frozen comparison. **The reader is frozen at `gpt-5.6-luna` for the whole v1-vs-v2
comparison**; a reader change would make every paired result a comparison of two things.

**Model verification fails closed only on an unlisted id** (`Models.ts`). A provider that cannot be
reached or whose `/models` is empty warns and proceeds; the run then fails on the first real call.
Refusing to start on a listing outage would make it look like a configuration error. The eval has
verified ids since #31; the server, demo and CLIs verify at startup too.

**Usage is per model** (`Llm.ts`). A run that reads with luna and judges with `gpt-4o` has two
prices; one number would be wrong by 10× on half of it. The service is `scoped` so `Layer.memoize`
can share one HTTP client across judged questions.

**`generateText` exists for the judge** (`Llm.ts`). The five LongMemEval templates end "Answer yes
or no only" and upstream scores `'yes' in response.lower()`; wrapping that in a JSON schema would
change the measurement. Its cache key uses `schema: { form: "text" }`. A cache entry that no longer
decodes means the schema moved: re-ask, never serve a stale shape.

**Cache key and stored prompt** (`Cache.ts`). Key = `sha256(model + system + prompt + schema)`, so a
prompt edit is a miss by construction. `system`/`prompt` are stored beside the value so a replay can
open one file and read the question; optional so entries written before the field existed still
load instead of costing a fresh call.

**Env-derived settings are read per call, not at module load** (`Gather.ts` `readTimeoutMs`,
`Select.ts` `selectModel`, `Sufficiency.ts` `sufficiencyModel`). CLIs call `loadDotEnv()` in their
body, but ESM evaluates the whole import graph first, so a module-level constant from `process.env`
is frozen before `.env` is read — the `PALIMPSEST_READ_TIMEOUT_MS` override was silently ignored for
exactly the cold-walk measurement it exists for. `loadDotEnv` is never an import side effect;
existing environment wins.

## packages/dataset

**`session.key`, not `sid`** (`LongMemEval.ts`). 13 of the 500 `_s_cleaned` haystacks list the same
session id twice — identical content inserted at two dates. Repeats get a `#n` suffix; `sid` stays
raw so `answer_session_ids` still matches. Every Turn key downstream is built from the key; hydrating
by the bare id reads the *other* conversation without erroring (`test/live/arms.probe.test.ts`).

**`session_ord` from the timestamp** (`LongMemEval.ts`). `haystack_dates` is unsorted in 211 of 500
S questions and 34 of 500 oracle questions; ties fall back to file position so the order is
reproducible.

**No streaming loader** (`Load.ts`). `longmemeval_s_cleaned.json` is 265 MB, parses in ~1.5 s into
~0.9 GB of heap, inside Node's default budget. Longest turn: 76 560 characters.

## packages/palimpsest — ingest

**Every write is a content-addressed `MERGE`** (`ClaimGraph.ts`). Re-running a session is the same
ids and the same values, which is what lets an ingest be retried, resumed, or re-keyed after a
prompt change without a delete step the engine cannot do.

**`ALIAS_SEPARATOR = "\u001f"`** (`ClaimGraph.ts`). HydraDB properties are scalars — no list type —
so aliases are one string joined by the ASCII unit separator, which the dataset's text cannot contain.

**`reconcileAll` is a fixpoint decided once per ingest** (`ClaimGraph.ts`, `Canon.ts`, `Ingest.ts`).
Reconciling per session as the graph grows is not idempotent: session 1 sees only earlier sessions
on the first pass and all of them on a re-ingest, so a canon merges on the second run that did not
on the first and the slot count moves. A sequential "first canon to claim a key wins" pass is not a
fixpoint either ("template" survived as a canon while being an alias of "journal"). Entities are
grouped by connected component over match keys (sorted stems of canon and every alias); an existing
canon always wins so a re-ingest never renames a written vertex. Each session writes only the
entities its own claims mention, so a 48-session haystack does not rewrite 2 200 entity vertices 48
times.

**`Token.df` and `Slot.n_claims` counted while writing** (`ClaimGraph.ts` `writeCounts`). The
aggregate join blows the 30 s cap once a few users share the store; a whole-user ingest holds the
exact answer in memory. Tokens that only `NAME` an entity get a `df` too, so idf has a number for
every anchor.

**`df` read via `MSpaths` with `pathCount: 1`** (`ClaimGraph.ts` `readTokenDf`). A single-session
ingest must add to counts the history already holds, and there is no batched read by id. The
per-source path cap is used instead of fought: one path per token, the source node carries `df`, and
a token with no `HITS` edge returns no path and is 0.

**`Claim.kind` is a per-user constant** (`Keys.ts`). `MSpaths` selects targets on a property; a
constant-valued selector returns every source→claim pair at the default `pathCount` (`CONTEXT.md`).

**Extraction is order-independent and shared** (`Ingest.ts`, `Canon.ts`). A session is extracted
knowing nothing about the user, so the call is keyed by session content and shared by every user
whose haystack contains it. LongMemEval_S references 23 867 sessions of which 19 195 are distinct:
~20 % of the extraction bill, and a re-key under a new uid is free. All sessions go out at once
under the `Llm` semaphore — 48 serial round trips is half an hour, concurrent is three minutes.

**Append-only `session_ord`, idempotent by session** (`Ingest.ts` `ingestSession`). `session_ord =
User.n_sessions + 1`; inserting in the middle would renumber later sessions and invalidate every
`at_session`. Vertices are content-addressed but the *counts* are not, so the Session vertex is
checked by id first — posting twice would inflate every `df` it touched.

**Supersession runs last, per slot, over the ordered history** (`Supersede.ts`). Whether a claim
replaces another is only visible against the whole slot: two hobbies are additive, two addresses are
not. The model works in 1-based positions so the prompt carries no `uid` and one slot history is one
cache entry for every user that has it. Structural rules stay in code: forward only, `at_session` =
the newer claim's session, single-claim slots never sent.

**`foldSupersessionEdges` takes the earliest replacement** (`Supersede.ts`). The prompt asks for a
chain but nothing forbids 1→2 *and* 1→3; with two edges out of one claim the label would depend on
the order HydraDB returned paths in, which would falsify the determinism hash. Earliest wins, claim
key breaks ties.

**Tokenizer is deliberately dumb** (`Tokenize.ts`). Ingest and question meet only at the token
string, so agreement matters more than linguistics: the trailing `e` is stripped from every form
("move"/"moved"/"moving" → "mov"); over-merging costs precision convergence absorbs, under-merging
costs recall nothing recovers. Stopwords are function words only — "new", "old", "time", "day" are
kept because `knowledge-update` and `temporal-reasoning` turn on them — and are checked on the
surface form ("note" stems to "not"). `WORD` keeps an internal apostrophe so `Wells Fargo's`,
`39.7 lbs`, `gpt-4o` behave. Keywords come first in `claimTokens` so the write-time query expansion
survives `MAX_TOKENS_PER_CLAIM = 24`.

**`Object.hasOwn(IRREGULAR, word)`** (`Tokenize.ts`). A plain object literal inherits
`Object.prototype`, so `IRREGULAR["constructor"]` is the Object constructor and `base.endsWith`
throws. "constructor" is the only word that reaches it — in any conversation about code — and it
crashed the BM25 baseline, which tokenises every turn. Cannot move an existing `tkey`: the input
previously threw.

**Extraction returns quotes, not offsets** (`Extract.ts`). Model offsets are a few characters off or
nonsense; a verbatim quote located in code is exact by construction. Three tiers (exact, whitespace,
markdown-noise — models drop `**bold**` when quoting; that tier cut dropped spans 128 → 15), and an
unlocatable quote is dropped and counted. `Schema.NullOr`, not `optional`: OpenAI strict output
requires every property present. The attribute vocabulary is closed-ish because slot collisions are
what makes supersession fire; the day-1 prompt that let every preference become `me | preference`
put 100+ claims in one slot.

**Turn chunking** (`Chunk.ts`, `CHUNK_BYTES = 30_000`). Four of 246 750 turns exceed the 32 743-byte
cap and they are the long assistant outputs `single-session-assistant` asks about. The chunker
iterates code points so a surrogate pair is never split. `Session.n_turns` is denormalised because
the `HAS_TURN` join measured 19.2 s at 26 users; `readTurn` is by id because `WHERE t.turn = $key`
scans every Turn in the store.

**Source key excludes extraction state** (`SourceTranscript.ts`). Re-extracting the same bytes must
not duplicate the verbatim transcript.

**Manifest schema v7** (`IngestManifest/Schema.ts`). v1 omitted `logical_session_id` from the
revision identity; a `source_revisions` table without `UNIQUE (tenant, uid, logical_session_id,
source_digest, extraction_generation)` is renamed `_v1`, re-keyed, and dropped, in one SQLite
transaction so an interrupted upgrade keeps the old table. `PRAGMA user_version = 7`.

**Canonical view target is the lexically first `(canon, id)`** per component
(`EntityCanonicalView.ts`), so a rebuild of the same input is stable.

**Commit lock is a separate SQLite file** (`IngestCommitLock.ts`). An exclusive transaction per user
held while stage effects run; process death releases the OS lock and the manifest resumes the same
commit id. A contender gets a typed conflict instead of racing projections or blocking the event
loop on SQLite's busy timeout. Separate from the manifest DB so transactions do not nest.

**Descriptors are explicit and canonically serialised** (`SourceIdentity.ts`). `canonicalJson` is
insertion-order independent; the extraction generation names model, prompt hash and schema hash so
a provider revision cannot masquerade as the same output. Derived assertions without a linked
verbatim span are never projected (`DerivedAssertion.ts`).

## packages/palimpsest — read path

**Arms run four at a time** (`Gather.ts`). The engine degrades under read concurrency as it did
under write concurrency (measured); eleven simultaneous walks are slower in wall clock than four and
unkind to a concurrent eval. The spec said six.

**`DEFAULT_READ_TIMEOUT_MS = 25_000`** (`Gather.ts`). The engine's cap protects the node; by the time
it fires the caller has spent 30 s of an 8 s budget. This protects the ask. v1 fails the ask on it;
v2 reports a timed-out *optional* arm in the receipt. `PALIMPSEST_READ_TIMEOUT_MS` raises it only to
*measure* a read the ceiling would hide (the benchmark's cold pass uses 115 s).

**Slot expansion is optional and `Either`-wrapped** (`Gather.ts`). #27's rule: an optional arm that
trips its ceiling is reported, the convergence walk is not optional. `slotClaims` exceeded 25 s on
one batch of four users twice on a warm node and took the run down. Both pipelines cap Query 2 at
the top 25 candidates, but v2's union fills more *distinct* Slots so Query 2 reads more. Only a
*limit* degrades; an unavailable node or parse error still throws.

**`totalClaims` memo** (`Retrieve.ts`). The idf denominator is read off the `User` vertex (~100 ms)
concurrently with Query 1, so the memo buys one round trip per repeated user, not latency. It is
forgettable (`forgetUser` after a live ingest) so an ask never scores against a stale denominator.
A user with no `User` vertex dies loudly: a total of zero flattens every idf. The denominator is the
whole-history count, not as-of — a constant factor changes no order, and the receipt says so.

**`anchorsReachingClaims`** (`Retrieve.ts`). The spec's A1 is "no anchor token exists"; this is "no
anchor reached a claim", the weaker and more useful test — a Token with no `HITS` edge is
indistinguishable from a missing one for the verdict.

**`graphMs` vs `askMs`** (`Retrieve.ts`). `graphMs` starts after the anchors call and ends at the
last read, never includes an LLM round trip; 1.5 s p50 warm is a claim about the index, 8 s about
the product. Hydration happens in `Reader`; the eval adds `hydrateMs` for the whole graph cost.
Supersession edges for the whole union are read *before* the selector — 120 keys and 30 keys are
the same round trip — so every graph read sits in one contiguous window.

**Verdict rule** (`Retrieve.ts`). A probe hit (an `(entity, attribute)` the question named) or a
sub-question hit (converged on words the question contains) can carry a verdict alone; discovery
guessed and a slot-mate came along, so neither can. Time scope runs only when the question carried a
date; `questionDateInt` is 0 otherwise and every date stage is skipped rather than run on year zero.

**Ablations off means skipped** (`Retrieve.ts`). `--no-discovery` must not pay for the round trip it
measures; `--no-select` must not pay for the LLM call. Otherwise the latency column is meaningless.

**Second pass = same arms, wider** (`Retrieve.ts` `extraTerms`). The sufficiency check's missing
stems join the convergence and discovery sources; only what is searched for differs.

**`fast` profile** drops the sufficiency check and its second pass — the demo's 5 s answer that is
occasionally thinner beats an 8 s one. The HTTP API defaults to `fast`.

**`beforeAsOf` runs before the verdict and the top-K cut** (`Scoring.ts`). Spec §3.4 put as-of at
step 5 and is wrong (erratum in the spec): a receipt computed over claims the memory should not have
yet reports anchors resolving against future claims and lets top-K be consumed by them. `applyAsOf`
still runs later for supersession edges and Query 2 slot-mates.

**`convergenceThreshold = min(2, |anchors|)`** (`Scoring.ts`). The one tunable; `min` so a one-word
question ("Nibbles?") can be answered. The reader's `NOT_IN_MEMORY` is deliberately not an
`AbstentionReason`: the retrieval receipt cannot explain it.

**Arm priority** (`Arms.ts`): probe > sub-question > convergence > discovery > slot-mate. Provenance
is what the union cap sorts by, what the receipt shows, and what the error-class table needs. A
claim several arms reached keeps the best of each (lowest priority, highest convergence, shortest
path).

**`UNION_CAP = 120`** (`Arms.ts`). A prompt budget: the selector reads this table, and past ~120
rows of id/text/date/speaker/status the listwise call loses rows in the middle.

**`ARM_CAP = 60`** (`Arms.ts`). A broad convergence walk returns hundreds of claims with a
convergence-1 tail no selector keeps; sixty is where the tail is all noise on dev. Applied *inside*
`unionArms`, after the as-of cut and before the union cap — the probe and slot-mate arms are already
bounded by the Slots they name.

**As-of before any cap** (`Arms.ts`). v1 cut Query 2's slot-mates to 40 *before* `applyAsOf`, so
post-`k` claims consumed the budget and were discarded and the scrubber lost recall at every
position but the last.

**Discovery seeds deviate from the spec** (`Arms.ts`). Two deterministic, LLM-free sources: the
entities a two-hop `Token→Entity→Claim` path passed through (a name the question's words reached —
the walk hands its raw paths on rather than re-reading), and terms from the top candidates' index
text ranked by rarity *within the candidate set*. The spec asked for idf from `Token.df`, which
`Scoring` only reads for terms that were already anchors — and an anchor discovers nothing.
Discovery is serial by construction and costs one round trip on the critical path.

**Probe arm** (`Arms.ts`). A missing Slot is an empty arm, not an error (the model proposes, the
graph decides). Probe claims score with zero anchors; arm priority keeps them, not a score.

**`MAX_SLOT_EXPANSION = 40`, `MAX_SLOT_MATES_PER_SLOT = 5`** (`Arms.ts`). v1 took the forty newest
slot-mates across all slots, so `(me, weight)` on a user who logs it weekly took the whole allowance.
Now: newest first (a knowledge-update question wants the replaced value), skip what an arm already
reached, five per Slot, forty overall; expansion is bounded to the top-K candidates, not the union.
Claims whose Slot the `FILLS` walk did not return share one `""` bucket. Both slot maps are kept
(`candidateSlots` and the read's) because `plan.slots` feeds the pack's adjudication labels.

**Selector guarantees** (`Select.ts`). `MAX_KEPT_TURNS = 30` counts turns, not claims (several claims
from one turn are one excerpt). `ALWAYS_KEEP_TOP_CONVERGENCE = 3`: convergence is the structural
verdict's own evidence. `enforceSelection` walks protected rows first — a probe hit has convergence
**0** by construction, so walking `ordered` and capping as it went discarded the guaranteed row
first, silently. Candidate order is deterministic because the prompt is the cache key. Listwise, not
per row: "keep every distinct item" is a statement about the set. A failed call *or an empty keep
set* falls back to v1 ordering and flags `selectorFallback` — an empty pack reads downstream as
"the memory does not contain it", a structural claim the selector was never asked to make.
`speakerShare` exists because 72 % of claims are assistant-sourced; the fix, if needed, is a
deterministic pre-sort, not a prompt tweak.

**Warm** (`User.ts`). `WARM_SOURCES_PER_WALK = 200`: measured 2026-08-31 on a 51-session user, 5
entity keys → 12 paths in 573 ms, 50 → 112 in 5.8 s, **2 292 → failure**, which the first version
reported as an empty result. `WARM_BUDGET_MS = 15_000`: the demo calls it on user select. Tokens
have no `User` edge and are reached backwards along `NAMES` from the entity fan-out; `deep`
(`HITS`, the user's whole inverted index) is off by default. Failures are counted, never zero.

**Time scope** (`TimeScope.ts`). The model supplies the *phrase*; the interval is computed in code
because date arithmetic has a right answer. Closed-open `[start, end)` over `YYYYMMDD` integers
(the graph's own form), so scoping is an integer comparison. Unrecognised is `null`, not a guess.
`monthIndex` uses `startsWith`: three-character equality made "decade" December, "junior" June,
"marathon" March. "this weekend" is the most recent Saturday–Sunday (questions are retrospective);
"last March" in February 2023 is March 2022; "<Month> <day>" without a year is the most recent
occurrence at or before the question date — the unshifted year put "december 3" asked in May 2023
in a window no claim could intersect. Month precision is `YYYYMM00`, year `YYYY0000`.
`UNDATED_SESSION_SLACK_DAYS = 7`: people talk about a weekend on the Monday after.
`MIN_IN_SCOPE_TO_DROP_REST = 10`: scoping is a boost, not a filter, because the extractor dates well
under half of claims. `intervalSentence` is route-independent.

**Understand** (`Understand.ts`). The model is asked only for what a model is good at (paraphrase,
decomposition, the attribute behind a noun); everything with a right answer stays in code. The
route drives exactly two things — reader prompt block and hydration granularity — and flags are
independent of it. Same `anchors` cache family as v1 (schema change already changes the key; the
system prompt says "version 2").

**`COUNT_PHRASE = /\bhow many\b/`** (`Understand.ts`, narrowed 2026-08-31). The widened
`how many|how much|how often|how numerous` put **21 of 36** first-run dev questions on the `count`
route (9 multi-session, 7 knowledge-update, 4 temporal); three of the four wrong count answers were
`INSUFFICIENT_EVIDENCE` because the check judges a count PARTIAL whenever an item might be missing.
Not over `temporal` ("how many years older" is subtraction). "currently" turns `fact` into `update`
when the vocabulary check would miss it ("where do I currently live").

**Reader never sees Claim text** (`Reader.ts`). A Claim is an index entry from an earlier model;
answering from it is a summary of a summary. `SPAN_CONTEXT = 300` characters each side at `span`
granularity; `turn` is the whole turn prefixed by the *preceding* one (the question that produced
an answer identifies it; the reaction after it rarely does). `TURN_ROUTES = assistant_output,
preference`: the answer *is* the message, and a qualification ("but only for short trips") is cut
by a 300-char window. Not `fact`/`count`/`update`/`temporal`/`multi_fact`: they need many claims in
one budget. A missing neighbour produces no path; at turn granularity every spilled turn is
reassembled. `ROUTE_RULES` is one system prompt plus a block, not seven prompts; v1's terse rule
survives only on `fact`. `--reader-route=off` gives v1's prompt byte for byte.

**Citation validation, one re-ask** (`Reader.ts`). A cited id not in the pack is fabricated; no
valid citation cannot be supported by the receipt. One re-ask shows the allowed ids; still nothing
is `NOT_IN_MEMORY`. A `NOT_IN_MEMORY` with no citations is not re-asked. A failed premise is a
refusal whatever the answer string says.

**`read` order: dedupe, label, budget** (`Reader.ts`). Dedupe first so a turn selected through three
claims is one excerpt before tokens are counted; label before budget so the cut cannot orphan an
`EARLIER STATEMENT` whose `CURRENT` partner it dropped; budget last so the receipt's number is what
the reader was charged. Excerpts are listed "CURRENT first, then superseded" — the previous "oldest
first" label was wrong exactly on knowledge-update questions. `readSpans` is the seam the baselines
use so they face the same prompt.

**`spanHash` over source spans** (`Pack.ts`, `Reader.ts`). The claim-key hash asks "same claims"
(an index question); a judge asks "same bytes". `claimHash` is kept beside it for v1 comparability.
Tuples use `sessionKey`, not `sid`.

**`CHARS_PER_TOKEN = 4`, `READER_TOKEN_BUDGET = 6000`** (`Pack.ts`). Four is the English figure the
520 000-char full-context cap was sized from and a placeholder: `readerInputTokens` and packed chars
are recorded side by side in every row so the ratio is a division. Luna's tokenizer is unverified.
6 000 is what the 1/30-of-full-context claim rests on.

**`ADJUDICATED_ROUTES = update, fact`** (`Pack.ts`). `(me, hobby)` is multi-valued; labelling older
entries `EARLIER STATEMENT` there tells the reader to discard true facts, which is how a count loses
half its items. `EARLIER STATEMENT` exists because supersession inference is incomplete: two
`CURRENT` claims in one Slot with different values.

**Budget** (`Pack.ts`). Cuts from the tail of the selector's ranking, never by size (that prefers
short evidence to relevant evidence); `protectedKeys` (probe hits) are never dropped, so
`overBudget` is reachable and reported rather than silent. `dropped` carries ids and reasons
(`budget` vs `selector` vs `turn_cap`) because a receipt reader asks *which* and *why*.

**`dedupeByTurn` merges only when one excerpt covers the other** (`Pack.ts`). Two claims 2 000
characters apart in one turn produce disjoint ±300 windows; merging them and widening `cs`/`ce` to
the union would drop one claim's evidence while `spanHash` records the union as seen. Kept after the
cleanup because the merge keeps the *winner's* window, not the union's.

## Sufficiency

**Why the stage exists** (`Sufficiency.ts`). On this benchmark misses are overwhelmingly
post-retrieval: the answer session is in the candidate set and the pack holds nine tenths of the
answer. Two outputs only — read, or go back once. Not an abstention oracle: 470 of 500 questions are
answerable, so the abstaining tier is a constant from a risk-coverage curve, not a per-question
judgement.

**`SKIP_ROUTES = fact, assistant_output`**. One excerpt either is the answer or is not, and the
reader's `NOT_IN_MEMORY` covers the second case; they are also the most common routes, so the check
would put an LLM round trip on the majority of asks. `--no-sufficiency` measures the reasoning.

**ABSTAIN_TIERS = []** (chosen 2026-08-31 from `results/risk-coverage-dev.md`). Refusing on PARTIAL would answer 46/47 correctly (risk 2.1 %) but abstain on 7 answerable questions (13.0 %, against the gate's ≤ 10 % false-abstention bound) and refuse one more `_abs` question (5/6 against 4/6). Answering everything gives 49/54, 9.3 % risk, 0 % false abstention and 4/6 `_abs`, exactly at the gate's ≥ v1 bound. The trade is three correct answers for one correct refusal, and the false-abstention bound decides it. `INSUFFICIENT_EVIDENCE` is implemented and tested and is not reached at this threshold. An earlier note cited numbers from a discarded run (46/54; 5 of 6 with and without the gate) and was wrong.

**The empty tier set does not disable the stage.** The check still runs and a `PARTIAL` with named
missing terms still triggers the one refined pass; only the tiers that turn an answer into
`INSUFFICIENT_EVIDENCE` are empty. `CONTRADICTED_PREMISE` is unaffected: it is gated on excerpts the
model cites that are in the pack *and* `CURRENT` — a premise cited only to a `SUPERSEDED` excerpt
*used* to be false, which is no reason to refuse. That guard keeps it from becoming a second,
unmeasured abstention path.

**A failed call is `EXACT` + `skipped`**, never `PARTIAL`: this stage can only withhold an answer,
so a provider error must not turn a working ask into an abstention. Own cache family so a run can
price the check separately from the reader. `PlanSufficiency.tier = "skipped"` is a real receipt
value, distinct from "the check said EXACT".

**`answerV2` is a function, not a service** (`Answer.ts`). Every caller already holds `Retrieve`
and `Reader`; what matters is that the loop lives in one place so the eval and the demo cannot drift
into different pipelines. The check reads the *packed* excerpts (what the reader sees), so it cannot
live inside `ask`. A contradicted premise short-circuits. Exactly one refined pass: a second PARTIAL
is information, a third is a budget. A second pass that abstains where the first answered keeps the
first answer — a second pass adds evidence, never removes an answer.

## packages/eval

**`fullCtxChars = 520 000`** (`bin/eval.ts`). The largest LongMemEval_S haystack is 513 954
characters (~128 k tokens), so B2 is never truncated and is never a straw man; `gpt-5.6-luna`
accepts it. If truncation ever fires, the *oldest* sessions go and the row records how many —
dropping the newest would flatter B2 on the knowledge-update questions it should find hard.

**`--batch N/M`** (`bin/eval.ts`). Contiguous by position in the sorted split, so the file name says
which questions are in it and it is stable across runs. A batch writes its own file and
`merge-batches` joins them; it never writes the whole-population file, because a partial file under
that name is what makes a results directory untrustworthy.

**Test-split refusals** (`bin/eval.ts`). `--skip-missing` is refused on `--split test`: a subset is
whichever users the ingest succeeded on, not a sample. `--slice` is refused once the split file
exists and has no gate record: `benchmarkSlice(100)` contains 40 of the 140 test questions and the
default invocation used to judge them. No escape hatch — that is how a test number becomes a
tuning signal.

**Gate** (`src/Gate.ts`). Read from **warm rows only** (a first-touch row is 26.5 s against 68 ms);
a file with no `graphMs` fails the criterion rather than skipping it. Regression is per question
type, not overall: +4 multi-session −3 knowledge-update is +1 and a broken feature. False
abstentions count structural abstention *and* the reader's `NOT_IN_MEMORY` — moving refusals
between mechanisms must not pass the gate. `GATE_BOUNDS`: `minCorrectGain 3` (more than a coin
flip on 54), `maxTypeRegression 1`, `maxFalseAbstentionPct 10`, `maxGraphMsP50 1500` (warm),
`maxReaderTokensP50 6000`.

**Extraction freeze by content hash** (`src/Splits.ts`). `BENCHMARK_EXTRACTION_DEPENDENCIES` are
declared constants naming the graph, not `git rev-parse HEAD` (which changes with every unrelated
commit); the real work is done by `prompt_template_sha256`, `output_schema_sha256` and the model
id. Not caught: a change to `Tokenize.ts` — a declared assumption under #22's graph freeze.
`splitByCached`: dev is whatever was already paid for (the 60 with cached anchors, reads and
judgements), so iteration costs $0 and v1 numbers exist for every one.

**`runtime_config_sha256`** (`src/RuntimeConfig.ts`). Read from the running container via
`docker inspect`, not the Compose file — the file says what was intended, the node says what a
latency number was measured against; the engine has no configuration endpoint. A prefix allow-list
(`GRAPH_*`, `MALLOC_*`, …) so `PATH`, `HOSTNAME` and rotated credentials are not "a different
runtime"; `GRAPH_AUTH_TOKEN_FILE` is provenance and never hashed. `canonicalise` is written out so
adding a reporting field cannot change historical hashes. **Never throws**: no daemon, a stopped
node or two matching containers records `{ sha256: null, reason }` — a null is answerable, a
fabricated hash is not.

**Paired statistics** (`src/Tables.ts`). McNemar exact, `p = 2·P(Binomial(b+c, ½) ≤ min(b,c))`
clamped at 1, no continuity correction (eight discordant pairs). The paired-difference CI is
`mean ± z·s/√n` over +1/−1/0 per question and reproduces the 2026-08-20 audit's hand-computed
−6.61 to +14.02 points for the 38/5/3/8 table. Quantiles are interpolated (R type 7) since
2026-09-04, whose p50 is the gate's mean-of-middle median; the committed dev latency table moved
240 ms / 880 tok → 246 ms / 890 tok, the numbers `results/gate-dev.md` carries. `errorClass` is a
funnel — retrieval, then selection, then reader — and v1 rows that reached the answer session are
`reader`.

**Reader A/B** (`src/ReaderAb.ts`, `bin/reader-ab.ts`). Population: `single-session-preference`
and `knowledge-update`, the routes the research predicted the rules matter on. Arm B re-reads the
*same spans* via `readSpans` with v1's prompt so the arms saw identical bytes; no warm pass, because
it reports no latency.

**Stats `--tokens`** (`bin/stats.ts`). The only remaining store-wide scan, opt-in: there is no
`HAS_TOKEN` edge, so a top-`df` listing reads the Token label — 8.7 s at 26 users. Nothing on the
product path does this.

**Slices** (`src/Slice.ts`). `stratifiedSlice` round-robins the six `question_type`s in `question_id`
order; the 30 `_abs` questions carry their base type, so a plain 100-slice took whichever `_abs` ids
sorted early (the 20-slice got 2 of 30). `evalSlice` takes all 30 plus a stratified remainder, sorted
by id so results files diff line for line. `benchmarkSlice(N)` is what `--slice N` means everywhere
(ingest, gate, harness): below 30 it is the untouched `stratifiedSlice`, so the day-1 and day-3
numbers keep their meaning; at or above the file size it is the whole benchmark.

**BM25 baseline** (`src/Bm25.ts`). Dependency-free so the comparison isolates the index structure:
same `stems()` tokenizer, reader prompt and judge as Palimpsest; whole turns as spans (cutting a
window would invent a span the baseline never produced), returned chronological like the graph
path, all `CURRENT` because a term index has no supersession — that absence is the comparison.

**Judge** (`src/Judge.ts`). Templates copied verbatim from LongMemEval `src/evaluation/evaluate_qa.py`
(fetched, not typed). Deviations: upstream pins `gpt-4o-2024-08-06`, this uses the `gpt-4o` alias and
records the resolved model per row; upstream caps at `max_tokens: 10`, the reply is free text and
scored by the same `'yes' in response.lower()`. An unknown question type throws (upstream raises
`NotImplementedError`). Judgements are cached by model + prompt so a table re-run is $0 and stable.

**Oracle ceiling** (`src/Oracle.ts`). `answer_session_ids` matches `session.sid`, not `key`, so the 13
haystacks with a duplicated sid include both revisions — the generous reading, right for a ceiling.

**`step-load --edges N`** (`bin/step-load.ts`). Edge counts are exact on an N-user sample from
source-driven `MSpaths` walks (indexed, never a label scan) and extrapolated as `ratio × claims`,
labelled as such. A sample because `HITS` alone is up to 24 paths per claim — five users is minutes,
two hundred an hour of read load. Walks run sequentially (reads degrade under concurrency like
writes do) and never while an ingest runs. `HAS_ENTITY`/`HAS_SLOT`/`HAS_SESSION`/`HAS_TURN`/
`SUPERSEDED_BY` are not walked: `UserStats` holds those counts. The row carries
`runtime_config_sha256` because a cache-off and a cache-on row are not the same measurement.

**`ingest-slice` retries** (`bin/ingest-slice.ts`, `--retries 1`, `RETRY_PAUSE_MS = 30 000`). Only
`HydraLimitError`/`HydraUnavailable`/`HydraEngineError` are retried — a 30 s refusal or a lost lease
describes the node, not the user; parse, schema and identity failures return the same answer every
time. The pause keeps the retry out of the pile-up that caused the refusal. `--skip-existing` is one
~100 ms read by id, *not* wrapped in `either`: a failed read means the node is down or read-only and
pushing 200 users through that is worse than stopping. Without it every earlier user's ~4 000
vertices and ~12 000 edges would be re-`MERGE`d per step.

**Backfill** (`bin/backfill-user.ts`). The one place that runs store-wide label scans on purpose: a
graph written before the `User` vertex existed is the only source for its own entity and slot sets
(~10 s per user at 26 users), which is why it must run *before* the next ingest. Re-keying to a
fresh prefix would cost the same wall clock and detach every handoff number from its keys. Turn
counts come from the dataset file, not the 19 s `HAS_TURN` join.

**Splits are committed before the first v2 result** (`bin/splits.ts`). "We did not tune on test" is
only checkable if the id lists were fixed in history first. Re-running is a pure function of dataset,
slice and cached row ids, except it never overwrites a gate record; `--check` records how many of the
population are fully ingested, because if the capacity gate trips mid-ingest the population *is*
whatever finished. A cached dev id outside `benchmarkSlice` dies rather than making "dev ⊂ 200" false.

**Driver parameters** (`scripts/`). `ingest-cycling -RestartAtPercent 70` (range 10–89) sits below
the capacity gate's 90 % so the restart is scheduled, not an incident; `-ReadCache off` is the
measured default, `on` trades more restarts for fewer MinIO round trips (unmeasured).
`p0-hydradb-capacity-gate` threshold 0 is reserved for fault-injection tests. Under `StrictMode` a
one-element pipeline is a bare string with no `.Count` and a parenthesised native pipeline can yield
`$null` — hence the `@(...)` wraps in `hydra.psm1` and the materialised `docker port` output in the
restart matrix.
